Inline message

One sentence under a field that says what to type or what went wrong with it.

Overview

An inline message is one short sentence attached to a field: a hint before typing, an error after a failed submit, or a confirmation. It lives under the field it describes and is linked to it with aria-describedby. In v1 every inline message is an error at the composer (L2-002.1, L2-003.2, L2-004.4) or under a row being edited (L2-013.2).

  • Use an inline message when the fix is in the field. Use an alert when the problem is the whole list, and a toast for the result of an action elsewhere.
  • Never show an error before the person has submitted; the composer shows nothing while typing except the character counter from 160 characters.

Anatomy

  1. FieldThe control the message describes; gets aria-invalid="true" for errors.
  2. Icon (optional)16px, inherits the message colour; aria-hidden.
  3. Text14px medium (--text-body-sm at 500), tone colour; referenced by the field's aria-describedby.

Responsive behaviour

  • The message spans the width of its field and wraps; it never truncates. The task-limit sentence wraps to two lines at 320px.
  • At the composer it sits below the field row, inset 16px to line up with the input text, at every breakpoint (the Add task button collapses to its icon below 576px but the message keeps the full width).

Theming

Tone colour comes straight from semantic tokens: --color-danger-fg, --color-success-fg, --color-fg-muted for hints. There are no component tokens; to restyle, override the semantic role in a theme. In dark the error text lightens to --palette-red-300.

Accessibility

Role and pattern

A paragraph referenced from the field with aria-describedby, plus aria-invalid="true" on the field for errors (WCAG 3.3.1). In v1 the error paragraph also carries role="alert" so it is announced when it appears after a submit even though focus stays in the field. Hints are never live regions.

Keyboard

Nothing to operate: the component is not focusable.

Focus

Focus stays in the field (the composer keeps focus after a failed submit so the person can type the fix). The message is not focusable.

Labelling

The text names the problem and the fix in the field's terms ("Enter a task title."). It is read after the field's label because of aria-describedby. Icons are aria-hidden.

Motion

The message appears without animation. On an empty submit the composer field gives one short shake (.composer--shake, 250ms), removed under reduced motion (L2-024.2).

Touch

Not interactive. The message never covers the field or the Add task button.

Content

  • One sentence, ending with a full stop, telling the person what to do: "Enter a task title." not "Title is required".
  • When the cause is not obvious, state it and then the way out: "You have 500 tasks. Finish or delete some to add more."
  • Server validation text is shown as the server wrote it (L2-004.4); keep the API messages in plain language.
  • No "Error:" prefix, no apology, no exclamation mark (L2-025).
