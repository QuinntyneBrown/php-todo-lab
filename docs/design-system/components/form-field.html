Form field

A form field is the layout primitive around an input. It fixes where the label, hint, error and character counter go, and how they are wired to the control, so every input in the product reads the same way.

WCAG 2.2 AAStatus: stableUsed in v1<label for> + aria-describedby

Overview

Wrap every text field, textarea and select in .field. The field owns the vertical rhythm (--space-2 between parts) and the relationships: the label names the control, the hint and message describe it, the counter sits inside the control's edge.

Tasks v1 uses the field's parts in two compact places: the composer (visually hidden "New task" label, counter from 160 characters, message under the card edge) and the in-place title edit in a task item (named by aria-label, message under the input). Both keep the wiring even though they hide the visible label.

Anatomy

  1. Label.field__label, --text-label (14px medium). Says "(required)" in text, never only an asterisk.
  2. Hint (optional).field__hint, --text-body-sm muted. Sits above the control so it is read before typing.
  3. Control.field__control wraps the input so the counter and icons can sit inside its edge.
  4. Counter (optional).field__count, 14px tabular, inside the right edge; red at the limit.
  5. Messageinline message (.message--error) under the control; replaces nothing, pushes content down.

Variants

The parts are optional; the order is not. Label, hint, control, message.

The field follows its control's size; the gaps do not change. Counter padding grows with the control so text never runs under it.

Responsive behaviour

  • Label above the control at every breakpoint; never beside it, so long labels and 200% zoom never squeeze the input (L2-030.3).
  • Fields are full width of their column at XS; from MD a .form__row--split may put two short related fields side by side (see form layout).
  • Input text stays 16px or more at every size so iOS never zooms on focus (L2-028.3).

Theming

Label --color-fg-default; hint and required marker --color-fg-muted; counter --color-fg-subtle, --color-danger-fg at the limit; messages per tone. The control itself is themed through --input-* (see text field).

Accessibility

Role and pattern

Plain HTML: <label for> names the control; aria-describedby lists hint then message ids; aria-invalid="true" marks an error. No APG widget pattern is needed; see the WAI forms tutorial.

Keyboard

KeyAction
TabFocus goes straight to the control; label, hint, counter and message are not focusable.
Click on labelFocuses the control (the label is a larger target).

Focus

Only the control shows focus: accent border plus the --shadow-focus halo. When a submit fails, focus moves to the first invalid control (or an error summary on long forms).

Labelling

Every control has a programmatic label (L2-029.3), visible unless the context makes it obvious; the composer hides "New task" with .visually-hidden because the placeholder question and the Add task button make the purpose plain. Placeholders are never the label. The counter is aria-hidden while typing (it would chatter); the field announces only when the limit is reached.

Motion

None of the field's parts animate; messages appear without transition so they are never missed.

Touch

The label is part of the target; controls are at least 44px tall at the default size.

Content

  • Labels are nouns in sentence case: "Task title". No colon.
  • Hints state a constraint before it is broken: "Up to 200 characters."
  • Error messages say what to do: "Enter a task title.", "A task needs a title.". Server messages (422) are shown as sent (L2-004.4).
  • Counters read "165/200": typed over limit, no spaces, tabular figures.
