## Checklist

- [ ] I read CONTRIBUTING.md.
- [ ] Behaviour changes have a requirement, a detailed design, and a mock.
- [ ] Each acceptance test was written first and seen to fail for the expected reason.
- [ ] `composer check` passes in `backend/`.
- [ ] `npm run check` passes in `frontend/`.
- [ ] `npm run e2e` passes, if the user interface changed.
- [ ] Formatting changes are in separate commits from behaviour changes.

## Screenshots
  • The first pass is the checklist, not the diff
  • A behaviour change with no L2 id and no design is not ready, however good the code (AGENTS.md)
  • Exempt: documentation-only, test-only, mock-only, design-system-only

Then the commits

Expect

  • A reformat commit with no behaviour change (L2-056 criterion 6)
  • A test commit preceding or accompanying its implementation
  • A description that says how the failing run looked

Ask

  • "Which test failed first, and why?"
  • "Can the reformat be its own commit?"
  • "Which L2 does this trace to?"

A worked slice: an overdue filter

The illustration the backend layering design uses for the open/closed rule. Due dates are out of scope for the product; the mechanics are what matter.

  1. Artefacts. An L2 requirement with Given-When-Then criteria traced to an L1; a design under docs/detailed-designs; a mock if the UI shows the filter
  2. Failing tests. ListTodosTest: ?status=overdue expects 200 with only overdue rows. tests/Unit/Actions/ListTodosTest.php: a dataset row for the new case
  3. Run them. The feature test fails with 422: ListTodosRequest validates against the enum. The expected reason, written in the PR

Three edits, no Action changes

enum TodoStatus: string
{
    case All = 'all';
    case Active = 'active';
    case Completed = 'completed';
    case Overdue = 'overdue';   // 1. new case
}
/** @param Builder<Todo> $query */
public function scopeOverdue(Builder $query): void
{
    // 2. the new scope on the model
}
match ($status) {
    TodoStatus::All => null,
    TodoStatus::Active => $query->active(),
    TodoStatus::Completed => $query->completed(),
    TodoStatus::Overdue => $query->overdue(),   // 3. one arm, plus the fake
};
  • Run composer analyse right after adding the case
  • Larastan reports every match over TodoStatus that does not handle Overdue: the repository and the fake
  • C#'s switch exhaustiveness warning, enforced at level 8
  • ListTodos, ListTodosRequest, and the controller do not change (L2-044 criterion 6)

Illustrative code; the enum case and scope do not exist in the repository.

Green, then the pull request

  1. Unit test passes with the fake; feature test passes against MySQL; composer check green
  2. composer format in its own commit, if it changed anything
  3. Template filled in: the L2 id, and the failing-run reason in the description

Three small production edits, two tests, three documents. That ratio is normal here.

Writing the review

Lands

  • "L2-044 criterion 1: this controller method runs a query."
  • "Can the reformat be a separate commit? L2-056 criterion 6."
  • "This undoes the one-statement update; see docs/detailed-designs/api-platform/persist-todos."

Does not

  • "Move this."
  • "Drop the reformat."
  • "I'd have used save() here."

When the tests are good, the artefacts are present, and composer check is green: approve. The gates exist so review can spend its time on design.

Things to remember

  • Order: artefacts and commits, then code in request order, then tests, then tooling
  • Checklists: short and mechanical, one per layer
  • Deliberate: string ids, one-statement updates, raw-attribute Resources, the committed connection, inline narrowing, exhaustive match, guarded $fillable
  • A slice: requirement, failing test with its reason, smallest implementation, green check; Larastan finds every match a new case touches
