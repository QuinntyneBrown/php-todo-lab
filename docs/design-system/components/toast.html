Toast

A brief message at the bottom of the screen that confirms a change and offers Undo, or says a change could not be saved.

WCAG 2.2 AAStatus: stableUsed in v1

Overview

A toast confirms what just happened, out of the way, and offers the one action that reverses it. The product has exactly two kinds: the undo toast after a delete or Clear completed (L2-015, L2-017), and the error toast when a change could not be saved (L2-004.3, L2-010.2, L2-013.4, L2-015.7, L2-014.5). One toast at a time, bottom centre, clear of the safe-area inset; a second one replaces the first.

  • Use a toast for the result of an action the person just took somewhere else on the screen.
  • Use an alert for conditions that persist (offline, load failed) and must stay visible until they change.
  • Use an inline message for problems with what is being typed; never a toast.
  • Never use a toast for something the person has to read before continuing; there are no modals in v1 (L2-022), so destructive actions are undone from the toast instead of confirmed up front.

Anatomy

  1. Container--color-bg-inverse, --radius-lg, --shadow-4; 52px minimum height, up to 26.25rem wide.
  2. MessageMedium weight, one short sentence in the past tense; the live-region text.
  3. Action (optional)A ghost button in --color-fg-inverse-accent; 44px tall, 12px radius, concentric with the container.

Two variants in the product. The tone of a confirmation comes from its words, not its colour; only failures change colour.

With an icon or a dismiss button

Available for future messages; v1 does not need them. Icons inherit the toast text colour, so the inverse surface keeps one contrast pair in both themes. A dismiss button is required only for toasts that do not time out.

Icon and dismiss are optional parts. Icons are aria-hidden; the dismiss button is labelled.

Sizes

Toasts have one size: they fill the width up to 26.25rem and grow in height with their message.

States

The toast itself is not interactive; its states are those of the action. Pointer and focus are forced with data-state. There is no disabled state: if the action is unavailable, the toast is not shown with it.

  • Entering: slides up 12px and fades in over --duration-slow (250ms) with --ease-enter.
  • Holding: 6 seconds for undo toasts, extended while the pointer is over it or focus is inside it (WCAG 2.2.1). Error toasts follow the same timer; the reverted state on screen is the persistent record.
  • Leaving: .toast--leaving fades down over --duration-base with --ease-exit, then the element is removed.
  • Replaced: a second delete replaces the toast and its Undo now targets the newer delete.

Responsive behaviour

  • The region is fixed to the bottom of the viewport at every breakpoint, centred, with 16px side gutters and bottom: calc(16px + env(safe-area-inset-bottom)) (L2-028.5).
  • XS: the toast spans the full width minus the gutters. SM and up: it stops growing at 26.25rem and stays centred under the 560/640px task column, so it never covers the composer or the header.
  • The page reserves --layout-safe-bottom (96px + safe area) under the list so the last row can always be scrolled clear of the toast; the focused row is never obscured (WCAG 2.4.11).
  • Long messages wrap; the action stays on the same line, vertically centred.

Theming

The toast reads four component tokens: --toast-bg, --toast-fg, --toast-action and --toast-action-hover. The default maps them to the inverse roles, so in light the toast is ink on the pale canvas and in dark it flips to a pale toast on the dark canvas: it always stands apart from the page. .toast--danger remaps them to the danger solid. Buttons inside a toast take --toast-action as their label and focus ring colour, because the page focus ring is too close to the inverse surface in dark.

/* A brand toast for a future theme */
[data-theme="partner"] .toast { --toast-bg: var(--color-accent); --toast-fg: var(--color-fg-on-accent); --toast-action: var(--color-fg-on-accent); }

Accessibility

Role and pattern

A persistent live region (.toast-region) exists from page load; toasts are inserted into it. Undo toasts use role="status" (polite), error toasts role="alert" (assertive), following the APG Alert pattern. The same words are also sent to the polite announcer (L2-031): "Task deleted", "3 tasks cleared". Specimens on this page omit the roles so the page does not announce on load.

Keyboard

KeyAction
Ctrl/Cmd+ZUndoes the last delete or clear while its toast is showing, from anywhere on the page except inside a text field.
TabReaches the Undo button in DOM order (the region is the last element in main); focus inside pauses the timer.
Enter, SpaceActivates Undo; the toast closes and "Task restored" is announced.
EscNo effect; the toast leaves on its own timer.

Focus

A toast never takes focus (it would pull the person away from the list). After Undo, focus moves to the restored task's checkbox so keyboard users land on what came back; if focus was on a deleted row, it moves to the next row, never to body.

Labelling

The message is the accessible content; the action's visible label ("Undo") is its name. Do not add an aria-label to the toast. Counts are written out in the message ("3 tasks cleared") so the announcement stands alone.

Motion

Slide-and-fade in (250ms) and fade out (200ms). Under prefers-reduced-motion the tokens zero both durations, so the toast simply appears and disappears.

Touch

The Undo button is 44px tall (L2-028.1) and sits 4px inside the toast edge. Hover pause has a touch equivalent: the 6s timer restarts when the toast is touched.

Content

  • Past tense, object first, no subject: "Task deleted", "3 tasks cleared", "1 task cleared". The verb matches the button that caused it (L2-025.2).
  • Errors say what failed and, when it helps, what to do: "Couldn't add that task. Try again." Never "Sorry", "Oops" or an exclamation mark (L2-025.1).
  • The only action label is "Undo". Do not add "Dismiss" text buttons or "OK".
  • Keep messages under about 40 characters so they fit on one line at 320px.
