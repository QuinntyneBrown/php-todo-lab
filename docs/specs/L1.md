# L1 - High-Level Requirements

## Scope, assumptions, and technology decisions

**Product.** A deliberately small to-do app: one screen, one list, a handful of actions. Its job is to let a person capture a task in seconds, tick it off with satisfaction, and get out of the way.

**In scope (v1):** create, list, filter (all / active / done), complete and reopen, edit title, delete with undo, clear completed.

**Out of scope (v1):** user accounts and sign-in, sharing, due dates, priorities, tags, sub-tasks, reordering, search, attachments, notifications, offline sync.

**Assumptions.**
- This is a learning project that runs locally on the developer's machine. It is single-user, with no authentication, authorization, or other security hardening. It must not be exposed to the internet.
- Input validation is a functional requirement (a task needs a sensible title), not a security measure.
- Code quality, accessibility, and responsiveness are still held to a high bar, because they are what the project teaches.
- A visual reference for the UI lives in `docs/mocks/todo.html`. The mock is the design target for L2-022 to L2-031.

**Technology decisions.**

| Concern | Decision | Reason |
|---|---|---|
| Backend framework | Laravel (current stable major), PHP 8.4+ with `declare(strict_types=1)` | Mature conventions, first-class validation, queues, scheduler |
| Database | MySQL 8.4 LTS, `utf8mb4` | Required by the brief; proper Unicode for task titles |
| Persistence | Eloquent ORM, migrations, factories, `SoftDeletes`, `HasUlids`; no raw SQL | ORM-only access removes SQL injection by construction and keeps the model expressive |
| API | Versioned JSON REST (`/api/v1`), Form Requests, API Resources, RFC 9457 problem details | Thin controllers, one place for validation and one for serialization |
| Frontend framework | Angular (current stable), standalone components, zoneless, `OnPush` | No NgModules, minimal runtime |
| Frontend state | Angular Signals (`signal`, `computed`, `linkedSignal`, `httpResource`) | Signals over RxJS for state; RxJS is confined to the HTTP boundary or absent |
| Local setup | `php artisan serve` + `ng serve` with an `/api` dev proxy; MySQL installed locally (Docker optional) | Simple to run and to learn from |
| Component files | Every component has separate `.ts`, `.html`, `.scss` files; no inline `template:` or `styles:` | Readable diffs, tooling support, enforced by lint |
| Design principles | SOLID on both tiers (single-purpose Action classes, interface-bound repositories, DI everywhere) | Testability and change isolation |
| Frontend formatting and linting | Prettier is mandatory and is the only formatter for TypeScript, HTML templates, SCSS, and JSON. angular-eslint (ESLint flat config) is mandatory for TypeScript and templates, with `eslint-config-prettier` so lint never rules on layout | One formatter, one linter, no overlapping rules |
| Backend formatting | Laravel Pint is mandatory and is the only PHP formatter, using the `laravel` preset (PSR-12 / PER Coding Style based) plus `declare_strict_types`, pinned in `backend/pint.json` | Canonical Laravel style, zero-config for contributors, enforces `strict_types` without a test |
| Shared editor settings | Root `.editorconfig` and `.gitattributes` (`eol=lf`) | Same whitespace and line endings on every OS, so formatter checks do not fail on Windows checkouts |
| Quality tooling | Pint, Larastan (level 8), Pest; ESLint (angular-eslint), Prettier, Stylelint, Vitest, Playwright, axe | One-command local checks |

## L1-001: Capture a task
The user must be able to add a task by typing a short title and confirming, in as few keystrokes as possible, with the task appearing immediately.

## L1-002: See my tasks
The user must be able to see all their tasks in one list, narrow the list to active or completed tasks, and see at a glance how many tasks remain.

## L1-003: Complete and reopen a task
The user must be able to mark a task done and undo that, with clear, rewarding feedback.

## L1-004: Edit a task
The user must be able to correct a task's title in place without leaving the list.

## L1-005: Remove tasks safely
The user must be able to delete a single task or clear all completed tasks, and recover from a mistake shortly afterwards.

## L1-006: Reliable data storage and API
The system must store tasks durably in MySQL and expose them through a stable, versioned JSON API with consistent success and error shapes.

## L1-007: A delightful, narrowly focused interface
The interface must be a single, calm screen that is fast, keyboard-friendly, and pleasant to use, with considered empty, loading, and error states and restrained motion.

## L1-008: Responsive layout
The interface must work well on every viewport from 320 px phones to large desktop displays.

## L1-009: Accessibility
The interface must be usable by people with disabilities and meet WCAG 2.2 AA.

## L1-011: Performance
The system must feel instant: efficient database queries and immediate visual feedback for every action.

## L1-012: Graceful failure and data consistency
The system must handle failure gracefully, never leave the UI out of step with the data, and keep stored data consistent.

## L1-013: Maintainable architecture
Both tiers must follow SOLID principles with the agreed stack: Eloquent ORM and layered services on the backend; signals-based state and separate-file components on the frontend.

## L1-014: Test-first delivery
Every behavior must be specified, covered by an acceptance test written before the implementation, and verified by automated quality gates.
