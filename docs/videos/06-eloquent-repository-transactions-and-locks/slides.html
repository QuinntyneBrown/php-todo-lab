The Eloquent repository: queries, transactions and locks

IQueryable, ExecuteUpdate, transactions and isolation, mapped onto EloquentTodoRepository

What you will be able to answer

  1. How a query is composed from scopes, and why the result goes through toBase
  2. Why update issues a query-level statement instead of saving the model
  3. How the 500-todo cap is enforced with a locking read in a retried transaction
  4. How the bulk operations stay all-or-nothing
  5. How the purge deletes in chunks without long locks

list(): scopes compose the query

backend/app/Repositories/EloquentTodoRepository.php
public function list(TodoStatus $status): Collection
{
    $query = Todo::query()->orderByDesc('created_at')->orderByDesc('id');

    match ($status) {
        TodoStatus::All => null,
        TodoStatus::Active => $query->active(),
        TodoStatus::Completed => $query->completed(),
    };

    return $query->get()->toBase();
}
  • Order matches the (deleted_at, created_at, id) index: MySQL reads it in order
  • Scopes are the reusable Where clauses; nothing runs until get()
  • toBase(): Eloquent collection → plain Illuminate\Support\Collection, the type the interface declares
  • Synchronous by design: no async, a query blocks the worker

counts(), find(), findDeleted()

backend/app/Repositories/EloquentTodoRepository.php
public function counts(): array
{
    return [
        'active' => Todo::query()->active()->count(),
        'completed' => Todo::query()->completed()->count(),
    ];
}

public function find(string $id): ?Todo
{
    return Todo::query()->find($id);
}

public function delete(Todo $todo): void
{
    $todo->delete();
}

public function findDeleted(string $id): ?Todo
{
    return Todo::onlyTrashed()->find($id);
}

find honours the soft-delete filter; findDeleted inverts it. That pair is what lets the Actions express different not-found rules.

update(): one statement, every column

backend/app/Repositories/EloquentTodoRepository.php
public function update(Todo $todo, array $columns): Todo
{
    // A query-level update writes every given column in one statement, even one
    // that matches a stale read, which a model save() would skip as clean.
    $values = array_map(
        fn (mixed $value): mixed => $value instanceof DateTimeInterface ? $todo->fromDateTime($value) : $value,
        $columns,
    );
    Todo::query()->whereKey($todo->getKey())->update($values);

    return $todo->refresh();
}
  • save() writes only dirty attributes, like SaveChanges; a concurrent patch could skip a column it considers clean
  • L2-043: every given column in one UPDATE. That is ExecuteUpdateAsync, not change tracking
  • Query-level updates bypass casts: dates go through fromDateTime (UTC)
  • refresh() returns the row as stored

createWithinLimit(): a locking read in a retried transaction

backend/app/Repositories/EloquentTodoRepository.php
public function createWithinLimit(string $title, int $limit): Todo
{
    // The locking read takes next-key locks on the scanned index range, so a
    // concurrent create waits here until this transaction commits, then counts
    // the new row. A deadlock is retried by the transaction attempts.
    return DB::transaction(function () use ($title, $limit): Todo {
        if (Todo::query()->lockForUpdate()->count() >= $limit) {
            throw new TodoLimitReached($limit);
        }

        return Todo::query()->create(['title' => $title]);
    }, attempts: 3);
}
  • Repeatable read alone lets two transactions both count 499 and both insert
  • lockForUpdate() → SELECT ... FOR UPDATE: next-key locks on the scanned range
  • The second create blocks until the first commits, then counts 500
  • A deadlock aborts one transaction; attempts: 3 retries the closure
  • Exceptions roll back and propagate: TodoLimitReached → 422

it('never exceeds the limit under concurrent creates', function (): void {

Bulk operations: lock, change, return, in one transaction

backend/app/Repositories/EloquentTodoRepository.php
public function deleteCompleted(): array
{
    return DB::transaction(function (): array {
        /** @var list<string> $ids */
        $ids = Todo::query()->completed()->lockForUpdate()->pluck('id')->all();

        if ($ids !== []) {
            Todo::query()->whereIn('id', $ids)->delete();
        }

        return $ids;
    });
}

public function restoreMany(array $ids): Collection
{
    return DB::transaction(function () use ($ids): Collection {
        $found = Todo::onlyTrashed()->whereIn('id', $ids)->lockForUpdate()->pluck('id');

        if ($found->isNotEmpty()) {
            Todo::onlyTrashed()->whereIn('id', $found)->restore();
        }

        return Todo::query()->whereIn('id', $found)->get()->toBase();
    });
}

A single whereIn statement each way; the locking reads make a concurrent clear and restore serialise.

Fault injection at the query log

backend/tests/Feature/Api/V1/ClearCompletedTodosTest.php
it('deletes all completed todos or none', function (): void {
    Todo::factory()->completed()->count(3)->create();
    DB::listen(function (QueryExecuted $query): void {
        if (str_starts_with(strtolower($query->sql), 'update')) {
            throw new RuntimeException('Simulated failure after the bulk update');
        }
    });

    $this->deleteJson('/api/v1/todos/completed')->assertStatus(500);

    expect(Todo::query()->completed()->count())->toBe(3);
});
  • DB::listen sees every executed statement; throwing on the first UPDATE aborts the transaction
  • No database mock: the real transaction rolls back
  • The .NET analogue: a SaveChangesInterceptor that throws
  • RestoreTodosTest does the same for restore (L2-017, L2-043)

purgeDeletedBefore(): small batches, short locks

backend/app/Repositories/EloquentTodoRepository.php
public function purgeDeletedBefore(CarbonImmutable $cutoff, int $limit): int
{
    return Todo::onlyTrashed()
        ->where('deleted_at', '<', $cutoff)
        ->limit($limit)
        ->forceDelete();
}
  • The only hard delete in the backend
  • forceDelete() returns the number of rows removed
  • The command loops in batches of 500 until a batch comes back short (video 09)
  • Each DELETE is small, so no long locks (L2-016 criterion 4)

Why the list follows the index, why TodoResource avoids per-row date parsing, and why the duplicate check is one pass.

Pitfalls

  1. $todo->fill($columns)->save() in update: the dirty-tracking gap is back
  2. Counting without lockForUpdate() inside the transaction: the cap is racy again
  3. Dropping attempts: 3: a deadlock becomes a 500
  4. Returning an Eloquent collection where the interface says the base collection (Larastan catches it)
  5. Loading and deleting one model at a time in a bulk operation
  6. Testing concurrency with mocks instead of racing real processes against MySQL

Things to remember

  • Queries: scopes compose like IQueryable predicates; toBase narrows the type
  • Update: one statement, every column, like ExecuteUpdate
  • Cap: a locking read in a transaction retried three times
  • Bulk: lock, change, return in one transaction; fault-injection tests prove rollback
  • Purge: small batches; latency: 200 ms keeps it honest
